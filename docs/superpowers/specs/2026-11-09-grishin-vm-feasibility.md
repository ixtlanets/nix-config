### Предлагаемый бюджет

Стартовый кандидат для отдельного рабочего desktop-гостя: **4–6 vCPU, 12 GiB RAM, 256 GiB thin disk** для полного согласованного рабочего набора; **160 GiB** только для урезанного фонового контура без полного Codex desktop-state/всех архивов/видео. Это предложение, не созданная конфигурация. Сервисный/проектный/media набор M1 — 102.57 GiB без пересоздаваемых dependencies/cache. Дополнительно lead обнаружил около 51 GiB Codex/agent desktop-state, не входивших в этот subtotal. **Обнаруженный набор полного рабочего desktop — примерно 154 GiB данных, до Linux и переустановленных зависимостей**, если сохранять всё учтённое состояние; минимально обязательный subset пока не установлен. Размер уточнять manifest/дедупликацией и ссылками. 128 GiB для полного набора недостаточно; 160 GiB имеет смысл только после явного сужения состава. Не клонировать personal VM вместе с личными данными и браузерами. Меньший старт 8 GiB возможен для фонового контура; 16 GiB обсуждать после измерения рабочего GUI. CPU shared, не выделенные физические ядра.

С новой VM 12 GiB запущенные лимиты составят 50 GiB, останется 11.60 GiB на гипервизор/накладные расходы/резерв. С одновременной Windows получится **62 GiB до накладных расходов**, то есть больше физической памяти. Поэтому **Windows держать выключенной** либо отдельно согласовать переразметку RAM. При 16 GiB рабочей VM без Windows останется только 7.60 GiB до накладных расходов.

Пул нельзя планировать до 100%: сохранить минимум порядка 15–20% (123–164 GiB) как инженерный резерв, ограничить рост логов/медиа/Frigate и мониторить Data%/Meta%. При первичном приросте порядка 175–195 GiB на полный work desktop (данные + OS/dependencies, инженерная оценка) останется около 177–197 GiB физически, если остальные гости не растут. Но полное заполнение нового диска 256 GiB оставило бы всего 116 GiB (~14%) даже БЕЗ роста нынешних гостей. Поэтому 256 GiB — виртуальный лимит, не гарантия одновременно доступного пространства: для первого этапа требуется согласованный фактический бюджет work guest порядка 180–195 GiB с общепуловым мониторингом и пересмотром хранения заранее; при верхней границе резерв на рост всех гостей до порога 80% пула лишь около 13 GiB, до 85% — около 54 GiB. Не выдавать это за большой долгосрочный запас. Это рекомендации, не настроенные сейчас квоты/пороги. Точный бюджет должен учитывать Linux, зависимости, rebuild caches и рост существующих гостей; snapshots не являются независимыми резервными копиями.

## Доступ, сеть и восстановление

Текущее имя SSH `um790pro` ведёт **в VM102 audiobook-ops**, не на PVE; физический PVE доступен по LAN с отдельной проверенной SSH identity. Персональная VM — `omarchy-vm`, LAN NAT22103. M1 проверен напрямую по LAN с `ProxyJump=none`: старый ProxyJump через `um790pro` больше не означает переход через гипервизор.

PVE подключён через Wi-Fi; M1 также использует Wi-Fi. TCP8080 на M1 (`192.168.1.174`) доступен из существующей personal VM; inference/model identity/auth не проверялись, а новая work VM ещё не существует и потребует отдельной проверки ACL. Пропускная способность копирования пока не измерена; PHY rate не равен полезной скорости. Сейчас work VM отсутствует. Существующий vmbr0 обслуживает personal/audiobook/Windows, vmbr1 — домашний контур. Отдельная VM не создаёт автоматически сетевую изоляцию: нужны согласованные firewall/ACL и своя Tailscale identity, отдельные рабочие browser profiles и credentials, отсутствие personal home mounts и автоматически скопированных A2A-каналов.

В PVE API `cluster/backup` и `cluster/replication` возвращают пустые списки, локальный dump-каталог пуст. Это не доказывает отсутствие внешних backup, но полноценное восстановление нового рабочего контура нужно отдельно проверить **до** cutover.

[Недавний runbook восстановления](</home/nik/migration/pve-kingston-install-2026-11-06/power-recovery-2026-11-08.md>) показывает зависимость гостей от boot/VPN gates. Новый work guest нужно проверять после reboot и при отказе VPN, не менять попутно существующие обходные/резервные узлы. Один PVE означает общий отказ питания/диска/Wi-Fi для personal и work; это консолидация, не HA.

Прямой remote audit M1 (macOS 26.5/arm64), 8–9 ноября:

В согласованном read-only представлении SQLite: 9 расписаний, 6 enabled/3 disabled, выполняющихся task_runs не обнаружено. Часть прошлых запусков ошибочна; это исходное состояние, не эффект миграции.
- Рабочий vault, используемый dashboard и несколькими агентами: около 49.76 GiB; каталог GR-проектов около 15.53 GiB без пересоздаваемых dependencies/cache. OpenClaw хранит дополнительные agents/browser/state/workspace данные. Связанные video work roots добавляют около 27 GiB; subtotal core OpenClaw/vault/GR — 75.60 GiB, с media — 102.57 GiB. Это **не включает Codex desktop history**. Полный согласованный объём уточнять по назначению, не копировать весь home.
- Дополнительный прямой замер lead, 9 ноября около 00:22 MSK: Codex state — 52,496,219,520 logical bytes (~48.89 GiB), Codex desktop Application Support — 2,079,817,896 bytes (~1.94 GiB), ещё около 0.43 GiB shared agents/Claude state. Итого добавка около 51.3 GiB. Это переносимый набор истории/состояния, НЕ обязательство переносить каждый cache; исключения согласовать, а resumable history, instructions, assets и dirty trees проверить в GUI. Скан не следует symlinks и не доказывает полноту внешних referents.
- GR News с работающим PostgreSQL 16.11, Next server и двумя Node worker consumers; логический dump/restore обязателен. На cutover quiesce обоих workers и web writers, не одного процесса. Dashboard и cloudflared/A2A — отдельные процессы/службы, не всё входит в OpenClaw.
- Секреты через exec/pass/GPG: не переносить значениями в Git/отчёты; отдельно безопасно подготовить ключи и возможность расшифровки. Skills OpenClaw ссылаются на соседние каталоги agents/claude; копии одного каталога OpenClaw недостаточно.
- Mach-O arm64 Node/cloudflared/openclaw-mac не исполнятся на Linux/x86; установить нативные аналоги. Apple host-desktop bridge и Keychain-зависимые browser helpers требуют замены/переавторизации. Наличие в браузере GR-профиля на Zenbook — дополнительная граница данных, не основание смешивать его с M1 без выбора авторитетной копии.
- Дополнительные внешние homes Brave/Chrome/LinkedIn helper в M1-аудите имеют суммарно около 20.90 GiB. Не все профили подтверждены рабочими и их нельзя бездумно добавлять/копировать целиком; необходим overlap-aware work-only manifest. Бюджет 175–195 GiB для исходного заполнения VM — оценка без безусловного импорта этих homes. Если обязательный набор с OS/dependencies приближается к 200–215 GiB, свободный общий пул после переноса составит лишь 157–172 GiB, а значит storage-growth gate становится ограничивающим: до cutover согласовать сокращение ненужных копий/вынос media или дополнительное хранилище, не трогая Samsung rollback автоматически.
- llama-server остаётся на M1 по исходному плану; его модель и RAM не включены в бюджет work VM. Если цель — оставить на M1 *только* llama-server, успешная замена всех Apple-only bridges является обязательным условием.

Наличие данных и число процессов не доказывают готовность всего рабочего сценария. Прямых изменений в очередях/SQLite/M1 не выполнялось; состояние активных задач необходимо перепроверить непосредственно перед будущим cutover.

## Границы переносимости и условия go/no-go

Linux desktop не является теоретическим препятствием сам по себе: на действующей personal VM проверены установленные `chatgpt-bin 26.1103.32239-1`, Brave, Chromium, TigerVNC и WayVNC (`pacman -Q`, 9 ноября). Но наличие пакета НЕ доказывает работоспособность именно рабочего Codex in-app browser, host-desktop bridge и сессий авторизации. Перенос macOS/ARM окружения — новая установка Linux/x86_64 с переносом данных, не запуск бинарной копии M1.

До остановки production необходимы: отдельный рабочий desktop, проверенный ручной перехват управления из клиента; работа агентного browser bridge на Linux; рабочие логины и необходимые OAuth grants; перенос запусков launchd в systemd; логическое восстановление PostgreSQL; сохранение SQLite/task/session state; доступ к оставшемуся llama-server без переноса модели в RAM UM790; backup и rehearsed rollback. Если macOS-specific host bridge не заменён и не проверен, оставлять соответствующий рабочий GUI на M1, а не объявлять полный перенос законченным.

Нельзя включать расписания/Telegram consumers на новой VM во время тестирования с production credentials. Отложенные/ошибочные задания требуют индивидуального решения, а не автоматического replay всей истории.

## Простой: метод оценки

Пока не финальный runbook. Окончательное окно зависит от текущего состава M1 и успешной Linux-репетиции.

1. Создать чистую отдельную VM, установить x86_64 зависимости, подготовить GUI/private access, первично скопировать данные, протестировать read-only/isolated-copy, не запускать production pollers/schedulers. Старые процессы продолжают работу.
2. На репетиции проверить OpenClaw, Codex GUI/in-app browser, внешний Brave, ручной перехват desktop, dashboard, почту/CRM/Telegram и LLM endpoint на оставшемся M1; отдельно macOS-specific bridges и OAuth.
3. В согласованное окно дождаться/завершить активные задания, остановить только work writers/сchedulers/consumers и запрещать их автозапуск на M1. Снять согласованные SQLite + WAL/SHM/прикладные snapshots и дампы PostgreSQL, досинхронизировать изменения. Не копировать живую PostgreSQL data directory между macOS ARM и Linux x86.
4. Запустить ровно один production экземпляр каждого потребителя на VM, проверить внутреннюю готовность, затем разрешить побочные действия, проверить результат. Зафиксировать missed cron jobs и дедупликацию, не отправлять тестовые рабочие сообщения без согласования.
5. Rollback: остановить новый writer, учесть новые записи и только затем вернуть старый. Одновременный запуск двух Telegram-поллеров и расписаний запрещён. M1 и его данные сохранить до принятия.

Предварительный инженерный ориентир после успешной репетиции: **30–60 минут** для переключения фоновых сервисов; закладывать **до 1–2 часов** на всё рабочее окружение с GUI/auth проверками. Это не измеренный SLA. Первичное копирование/установка/авторизации должны идти заранее и не входить в простой; если авторизация/browser migration впервые делается после остановки, окно становится непредсказуемым. Формула: drain + final delta / measured throughput + consistent DB export/import + startup + acceptance; полная остановка на всё копирование не требуется.

## Ограничения обследования
